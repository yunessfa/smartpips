# راهنمای استقرار نسخهٔ پایهٔ ممیزی SmartPips

## اول وضعیت این نسخه را بدانید
این بسته تکمیل تمام ۴۲ فاز یا تأیید سودآوری و ایمنی معاملات واقعی نیست. این محیط به Docker، PostgreSQL تولیدی، حساب صرافی و دادهٔ تاریخی معتبر بازار دسترسی نداشت. ابتدا روی **کپی جداگانهٔ PostgreSQL با بازیابی بکاپ** آزمایش کنید؛ اجرای مستقیم روی تولید توصیه نمی‌شود.

ZIP تحویل‌شده به GitHub push نشده است؛ `git fetch/reset` به‌تنهایی این تغییرات را دریافت نمی‌کند. ابتدا فایل‌های بسته را در شاخهٔ بازبینی/نسخهٔ جداگانه قرار دهید. `.env`، فایل‌های محلی، volumeها و کلیدها را از نسخهٔ موجود حفظ کنید. `git reset --hard` می‌تواند تغییرات commitنشده را پاک کند؛ این راهنما به آن نیازی ندارد.

## ۱. بکاپ و توقف نویسنده‌ها
- بکاپ PostgreSQL را با ابزار واقعی سرور/سرویس دیتابیس بگیرید؛ مسیر سرویس دیتابیس در این Compose فرض نشده است. بکاپ باید شامل schema و داده و قابل بازیابی باشد. یک فایل خالی یا تغییر نام یک فایل، بکاپ نیست.
- بکاپ را روی دیتابیس **جدا از تولید** بازیابی و شمار ردیف‌ها، کاربران، موجودی‌ها و چند معاملهٔ قدیمی را تطبیق دهید. نسخهٔ کد، تنظیمات و شناسهٔ بکاپ را ثبت کنید.
- قبل از تغییر schema، سفارش‌گذاری خودکار واقعی و همهٔ workerهای بیرون از Compose را متوقف کنید. اسکریپت فقط backend و demo-monitor همین Compose را متوقف می‌کند؛ نمی‌تواند سرویس‌های خارجی را کشف کند.
- مقادیر `.env` را در چت یا لاگ عمومی ارسال نکنید. هشدار Compose دربارهٔ متغیری مانند `ynk` می‌تواند ناشی از تفسیر `$` در مقدار تنظیمات باشد؛ تنظیم مربوط را محلی و بدون افشای مقدار بررسی کنید. خروجی کامل `docker compose config` ممکن است secret نشان دهد.

## ۲. بررسی در staging با کپی مستقل تنظیمات
در مسیر نسخهٔ جدید، با `backend/.env` مخصوص دیتابیس staging:

```bash
cd /home/ubuntu/smartpips

docker compose -f docker-compose.yml -f docker-compose.demo.yml build backend frontend

docker compose -f docker-compose.yml -f docker-compose.demo.yml run --rm --no-deps backend \
  python manage.py showmigrations accounts trades ctrader strategy

docker compose -f docker-compose.yml -f docker-compose.demo.yml run --rm --no-deps backend \
  python manage.py prepare_entry_audit --require-persistent-db
```

دستور آخر **پیش‌فرض فقط بررسی** است، نه اجرای migration. برنامهٔ قابل قبول فقط migrationهای اعمال‌نشدهٔ زیر است:
- `trades.0009_entry_audit`
- `ctrader.0002_oauthattempt`

نسخهٔ نصب‌شده باید پیش‌نیازهای `trades.0008_accounting_provenance` و `ctrader.0001_initial` را واقعاً داشته باشد. اگر تاریخچه/schema ناسازگار، پیش‌نیاز گمشده، جدول ازقبل‌موجود یا مهاجرت برگشتی گزارش شد، **توقف کنید**. با `--fake`، حذف جدول یا migration عمومی از مانع عبور نکنید. تاریخچهٔ قدیمی trades در نصب خالی conflict دارد و در این بسته بازنویسی نشده است؛ ابزار حاضر مخصوص ارتقای baseline نصب‌شده است، نه نصب صفر.

## ۳. اجرای کنترل‌شده، ابتدا در staging
مسیر زیر فقط مثال است؛ آن را با فایل واقعی بکاپ بازیابی‌شده جایگزین کنید:

```bash
BACKUP_FILE=/secure/backups/smartpips-verified.dump \
STAGING_VERIFIED=1 \
APPLY_AUDIT_MIGRATIONS=1 \
bash deploy/release-entry-audit.sh
```

`STAGING_VERIFIED=1` تعهد اپراتور به انجام بررسی است، نه آزمون خودکار؛ اسکریپت فقط وجود و غیرخالی‌بودن فایل بکاپ را بررسی می‌کند و نمی‌تواند صحت بازیابی آن را تضمین کند.

اسکریپت imageها را می‌سازد، وضعیت و برنامه را دوباره می‌خواند، backend/demo-monitor را متوقف، فقط دو migration افزایشی را اعمال و `manage.py check` را اجرا می‌کند؛ سپس backend و frontend را بالا می‌آورد. در صورت شکست، fail-closed متوقف می‌شود؛ خروجی را بررسی کنید و سرویس را کورکورانه تکراراً راه‌اندازی نکنید.

**demo-monitor پیش‌فرض خاموش می‌ماند** تا معاملهٔ خودکار بدون بازبینی دوباره فعال نشود. فقط پس از تست و با تصمیم خودتان `START_DEMO_MONITOR=1` اضافه کنید.

برای ساخت adapter پژوهشی اختیاری `backtesting.py`، `ENABLE_RESEARCH=1` به محیط دستور اضافه کنید؛ این گزینه جایگزین موتور پیش‌فرض نیست و تفاوت‌های اجرای آن در گزارش بک‌تست آمده است.

## ۴. چک‌لیست پذیرش staging و سپس تولید
- ورود دسکتاپ/موبایل، refresh پس از انقضای access token، CSRF و خروج را با حساب آزمایشی بررسی کنید.
- اطلاعات، PnL و attribution معاملات قدیمی باید بدون تغییر بمانند؛ snapshot خالیِ سابقه عمداً جعل/پر نمی‌شود.
- یک معاملهٔ دموی جدید بسازید؛ snapshot/hash و رویداد ENTRY ثبت شود؛ ویرایش snapshot رد شود؛ خروج دوباره نباید دوباره حسابداری کند.
- کدهای WAIT، دادهٔ نامعتبر و ریسک نامعلوم نباید سیگنال قابل اجرا یا سفارش واقعی تولید کنند. حساب/حدود ریسک واقعی هنوز نیازمند بازبینی venue-specific است.
- cTrader پس از مجوز جدید نیاز به انتخاب صریح حساب توسط admin دارد؛ state نامعتبر و درخواست GET برای تغییر حساب باید رد شوند. ارتباط قدیمی فقط با migration پاک نمی‌شود.
- هشدارها، استراتژی‌ساز، تحلیل، نمودار با ارتفاع قبلی، ژورنال و export را تست کنید. تست محلی رابط از fixture بوده و جای این پذیرش را نمی‌گیرد.
- گزارش analytics را با source مشخص بررسی کنید؛ آمار ترکیبی دمو/دستی را به عملکرد حساب واقعی نسبت ندهید.
- تنها پس از این پذیرش، همین ترتیب را با بکاپ تازه و پنجرهٔ نگهداری روی تولید اجرا کنید. سفارش واقعی را برای smoke test خودکار نفرستید.

## بازگشت
image/نسخهٔ قبلی و بکاپ را نگه دارید. migrationها افزایشی‌اند؛ بازگرداندن کد به نسخهٔ قبلی را ابتدا روی staging تست کنید و برای rollback، جدول‌های جدید را حذف یا migration را reverse نکنید. اگر داده آسیب دیده باشد، بازیابی باید طبق برنامهٔ DBA و پس از توقف تمام نویسنده‌ها انجام شود، نه با دستورات حذف volume.

هیچ‌کدام از این مراحل نیاز به `docker compose down -v` یا حذف دیتابیس ندارد.
